# Custom Pages and SEO

## Scope

Use this workflow when a user asks for a personal or campaign page, About, Contacts, portfolio, service page, event page, or another page managed by the uCoz Pages module. It complements the framework; it does not justify a site-wide framework publication.

## Page workflow

1. Call `templates_tool(action="page_list")` and reuse an existing page when appropriate.
2. Call `page_get` before changing an existing page. Preserve its ID, URL, parent, access, pending state, and unrelated settings.
3. Create with `page_add`, or update with `page_update`. Use `page_owntmpl=1` and a complete `page_tmpl` only when that page genuinely needs its own layout.
4. Reuse the active design system: the same frame width, type scale, color tokens, buttons, forms, dividers, focus states, and semantic SVG icons.
5. Link `/_st/my.css?v=<version>` in an independent full-page template. Increment the version manually after every CSS upload because tmaker does not rewrite custom page templates.
6. Put page-specific rules in a uniquely scoped section of the shared `3/3` stylesheet. Read `3/3` and patch that section for an incremental change; replace the whole stylesheet only during an approved complete redesign.
7. Browser-test the page beside the homepage and one module page at mobile and desktop widths.
8. Use conditions only for variables and permissions confirmed for that Pages template. Hide the complete dependent component when data is absent, and test both branches; do not copy framework-only page/module conditions into a personal page blindly.
9. When the page has breadcrumbs, reuse the active framework's exact breadcrumb component and separator symbol. Do not create a landing-page-specific arrow, font, spacing, or gutter.

Do not create a second unrelated visual system or upload `/css/style.css` merely because the page resembles a landing page. Do not republish tmaker to alter one Page.

## Shared shell

Prefer current global header/footer blocks when the Pages template context supports them. Otherwise reproduce only the necessary semantic shell with the same class names and stylesheet, keeping navigation, account controls, mobile drawer, `$POWERED_BY$`, and accessibility behavior consistent. Never copy stale standard-design scripts or asset paths.

## SEO variables in framework-generated templates

For each full-page template, call `get_variables` and use only confirmed SEO variables:

- `$SEO_TITLE$` for the document title;
- `$SEO_DESCRIPTION$` for the description meta tag;
- `$SEO_KEYWORDS$` for the keywords meta tag.

Keep a context-appropriate fallback title when SEO title is empty. In the framework source preserve `[TITLE]` as the fallback required by tmaker. Validate conditional syntax with `skeleton_validate`; never assume a variable supported by one module exists in every template.

Escape nothing by hand inside platform variables and do not print empty meta tags. Do not invent `$CANONICAL_URL$`, image variables, or other SEO codes absent from `get_variables`/the live rules.

## SEO fields for custom Pages

Set `page_meta_title`, `page_meta_description`, and `page_meta_keywords` through `page_add` or `page_update`. Write a unique human title and description that match visible content. Keywords are optional; do not stuff repetitions.

Inspect the rendered `<head>` afterward. Ensure there is one effective title and description and that the SEO module did not create duplicates. Add canonical, Open Graph, Twitter, or JSON-LD metadata only when their values are real, verified, and not already generated by uCoz. Never ship placeholder domains, fake social images, or schema values not visible on the page.

## SEO QA

- Title is unique, descriptive, and not duplicated with the site name twice.
- Description exists when useful and matches the page.
- Heading hierarchy contains one clear `h1`.
- Links have meaningful text; important images have useful `alt` text.
- Content remains usable without metadata or social scripts.
- Rendered source contains no literal unknown `$SEO_*` variable.
- Search and module pages inherit the same design and remain indexable according to the user’s preference.
